### Контекст / Легенда
Вы работаете в команде, отвечающей за платформу электронной коммерции, состоящей из нескольких микросервисов. Один из них, product-catalog, отвечает за предоставление информации о товарах. ## 2. Инструкция

#### 1. Запуск тестового стенда
Разверните микросервис, Prometheus, Grafana одной командой:

```bash
docker compose up -d --build
```

При изменении конфигурации prometheus пересоздавайте стенд командой
```bash
docker compose up -d --build --force-recreate prometheus
```
чтобы гарантировать, что все изменения подтянутся.

#### 2. Ознакомление

Для вас подготовлен проект. В проекте реализован базовый сервис на Go, который предоставляет API для получения информации о товарах. Сервис экспортирует различные метрики (counter, histogram) в формате Prometheus. Вам необходимо:

1. **Ознакомьтесь с метриками.** Поймите, какие метрики сейчас экспортируются (`internal/metrics`), как они собираются (`internal/metrics/middleware.go`) и какую информацию они предоставляют. Оцените, насколько текущий набор метрик достаточен для диагностики проблем производительности и стабильности. Пока не анализируйте код, где они используются. Вам нужно, не влезая в код сервиса поначалу, понять поведение сервиса как blackbox. В реальных сервисах могут быть сотни разных метрик и десятки тысяч строк кода. Чтобы понять, где искать проблему, обычно анализируют доступные метрики, а затем идут смотреть код на предмет оптимизации.
2. **Настройте сбор метрик.** Разверните сервис (используйте предоставленный docker compose). Настройте Prometheus для сбора метрик с этого сервиса. Убедитесь, что Prometheus успешно собирает и хранит метрики. Заготовка для конфига prometheus уже есть, но сбор метрик еще не настроен.

Можно конечно почитать долгую и нудную документацию <https://prometheus.io/docs/prometheus/latest/configuration/configuration/>, чтобы настроить файл `docker/prometheus/prometheus.yml` (не забудьте пересобрать с `--force-recreate`, чтобы конфиг подтянулся), а можно просто посмотреть готовые примеры вида <https://github.com/prometheus/prometheus/blob/main/documentation/examples/prometheus-docker.yml> и адаптировать их под docker-composer. А именно - собирать мы будем не с localhost, а по имени контейнеров (имя контейнера в docker вполне ресолвится через dns, так что смело указывайте его в конфиге).

3. **Сгенерируйте нагрузку.** Используйте k6 с предоставленным скриптом `load.js` для создания нагрузки на product-catalog. Инструкцию по установке k6 можно найти здесь https://grafana.com/docs/k6/latest/set-up/install-k6/. Команда для запуска `k6 run load.js`.
4. **Проанализируйте метрики в Grafana.** Создайте дашборд в Grafana для визуализации собранных метрик. Постройте графики:
    - RPS (Requests Per Second) (см. rate <https://prometheus.io/docs/prometheus/latest/querying/functions/#rate>)
    - Потребление памяти сервисом (можете использовать `go_memstats_heap_sys_bytes`)
    - Latency запросов (p95, p99) (см. <http://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile>)
    - Количество ошибок (5xx)
5. **Выявите источник проблемы.** На основе анализа дашборда в Grafana, определите источник медленной загрузки страниц (медленные api endpoints) товаров и периодических ошибок (api endpoints с 5xx кодами ответов).


**Вы нашли источник проблем (какой endpoint дает ошибки и тормозит)**

Теперь можно пойти в код, поправить “проблемы”, пересобрать проект, запустить нагрузку и убедиться, что все работает более стабильно.


**Дополнительное задание**

Сервис был запущен в 2-х репликах изначально. Первый скрипт load.js одинаково нагружал обе копии и метрики с разных инстансов “путались”.


Теперь изучите, как в prometheus добавить доп. labels для сервиса (пример <https://stackoverflow.com/questions/49829423/prometheus-add-target-specific-label-in-static-configs> или <https://signoz.io/guides/how-to-add-target-specific-label-in-prometheus/>), воспользуйтесь скриптом `load-uneven-replicas.js` для создания нагрузки и добейтесь четкого разделения проблем на созданных графиках, чтобы понять, в какой реплике есть проблемы. Только одна из реплик создает повышенное latency в сценарии с load-uneven-replicas.js. Этот кейс демонстрирует ситуацию, когда у вас есть перегруженная нода в k8s кластере, куда попала одна из множества реплик вашего приложения, и если смотреть на общие метрики по всем репликам, то вы увидите это повышенное latency (при условии, что запросы правильно составлены), но не поймете почему latency выросло, пока не найдете, что проблема только с одной из реплик, а не с вашим кодом.


В качестве имени такой label можете использовать k8s_node. Например, k8s_node=replica-1 для первой реплики и k8s_node=replica-2 для второй реплики приложения. Такой же label используется в готовом дашборде, с которым вы можете свериться.
