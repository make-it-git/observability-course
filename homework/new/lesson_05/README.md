# Домашнее задание: Анализ логов

## Цель

Научиться использовать логи для построения дашбордов в Grafana.

> **Disclaimer:** В общем случае метрики — это то, на что стоит полагаться для построения графиков, создания алертов и т. д. Но мы живем в реальном мире, где:
> * Метрик может быть недостаточно в разрезе конкретных частей системы.
> * Мы работаем с 3rd party продуктом, в который не можем вносить правки. Даже если в нем есть метрики, нам может потребоваться больше деталей из логов.
> * Метрик может вообще не быть, а логи есть практически всегда.
>
>

### Важное предупреждение о производительности

При работе с большими объемами (например, терабайты логов в сутки) любой запрос для визуализации логов даже на коротком интервале (за час) может быстро вывести из строя систему логирования при неправильном использовании.

Если вы откроете дашборд из 5–6 панелей с логированием за последний час и включите автообновление каждые 30 секунд, каждый запрос может требовать поднятия с диска (или из S3) 10–100 ГБ данных просто для отрисовки трендов.

*Аналогия:* Это эквивалентно тому, как если бы Grafana каждую минуту заставляла PostgreSQL выполнять `FULL TABLE SCAN` по таблице размером 100 ГБ.

## Задача

Репозиторий проекта: [https://github.com/make-it-git/observability-course/tree/main/homework/new/lesson_05/project](https://github.com/make-it-git/observability-course/tree/main/homework/new/lesson_05/project)

Проект реализует простое API, отдающее данные для конкретного `userID` в зависимости от региона запроса:

* **Эндпоинт:** `GET /user/{userId}`
* **Передача региона:** HTTP-заголовок `X-Region`

### Контекст проблемы

1. У проекта много регионов, но метрики отсутствуют (легаси).
2. Служба поддержки сообщает, что для некоторых пользователей приложение часто сбоит.
3. Балансировщик нагрузки / API Gateway отдают только обобщенные метрики: `200 OK` или `500 Server Error`. Из-за высокого общего трафика фоновые ошибки не видны на графиках метрик.
4. Чтобы найти проблему, необходимо проанализировать логи ошибок в разрезе регионов.

Сбор логов в **Loki** через **Promtail** уже настроен. Сбор через **OpenTelemetry Collector** находится в процессе настройки.

## Чек-лист выполнения

1. **Настройка Otel-Collector:**
* Подключите `otel-collector` в файле `docker-compose.yml` (в качестве подсказки используйте `lesson_05/log_delivery`).
* Настройте переменные окружения в секции `environment` сервиса (см. документацию [SDK Environment Variables](https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/) и [OTLP Exporter](https://opentelemetry.io/docs/languages/sdk-configuration/otlp-exporter/)):
* `OTEL_SERVICE_NAME=homework-service`
* `OTEL_EXPORTER_OTLP_ENDPOINT`


2. **Запуск и генерация нагрузки:**
* Запустите проект через `docker-compose`.
* Сгенерируйте нагрузку с помощью k6:
```bash
k6 run load.js

```




3. **Анализ логов (2 способа):**
* **Способ 1:** Через логи Promtail (фильтрация по label `docker_container`).
* **Способ 2:** Через логи OpenTelemetry Collector (требуется донастроить конфиг в `homework/lesson_05/infra/otel/otel-collector-config.yaml`).


4. **Проверка:**
* Найдите «ошибочные» регионы и сверьте их с исходным кодом сервиса.



> **Примечание:** Подключение Otel SDK требует аккуратности. В отличие от стандартного вывода в `stdout` (через `slog` или аналогичные библиотеки), ошибки в конфигурации OTLP-экспортера могут привести к молчаливой потере логов.
